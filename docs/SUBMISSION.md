# Сдача Results JSON 1.0 — Fantastic Four

Источник требований: официальное приложение к Student Guide, страницы 1–3, полученное 7 ноября 2026. Это инструкция подготовки файлов; сохранение файла не отправляет работу организаторам.

## Через сайт

1. Откройте раздел **«Сдача жюри»**. Название команды — **Fantastic Four**.
2. Для DEV выберите группу с исходными 60 чатами и 5 звонками. В текущей базе это `DEV`.
3. Нажмите **«Проверить готовность»**. Посмотрите число `ok`, `error` и причины ошибок.
4. Нажмите **«Сохранить файл для жюри»**. Сервер создаст `results/dev/results.json` в корне проекта. Прежний файл, если был, копируется в локальную папку `data/submission_backups`.
5. При необходимости нажмите **«Скачать копию JSON»**. Файл из папки загрузок — только дополнительная копия; для Git уже подготовлен файл в проекте.
6. Когда организаторы выдадут контроль, импортируйте его через API с фактическим `group_id`, выполните оценки и выберите эту группу в режиме **«Контроль»**. Экспорт проверит ровно 10 исходных чатов и сохранит `results/prod/results.json`.

Пока контроль не получен, корректного контрольного файла нет. DEV нельзя переименовать в PROD; вымышленные ID и пустой results.json не создаются.

Во время незавершённых заданий экспорт группы блокируется, чтобы не сохранить устаревший промежуточный результат. Дождитесь окончания или отмените ещё не запущенные задания.

## Через командную строку

Команды выполняются из корня проекта. Модельный API-ключ для экспорта и проверки не нужен: используются уже сохранённые результаты.

```powershell
python -X utf8 submission.py export --set dev --team "Fantastic Four"
python -X utf8 submission.py check results/dev/results.json --set dev
```

Для контроля вместо `<group_id>` укажите настоящую группу организаторов:

```powershell
python -X utf8 submission.py export --set prod --group "<group_id>" --team "Fantastic Four"
python -X utf8 submission.py check results/prod/results.json --set prod --group "<group_id>"
```

`check` сверяет файл с исходными диалогами выбранной группы: ID, количество и каналы, поля JSON, значения и ступени, номера реплик, веса, округление и независимый флаг грубой ошибки. Дубли полей JSON и NaN/Infinity отклоняются.

## Как формируется файл

| В приложении | В файле |
|---|---|
| Критерии 1–8 | contact, discovery, identification, consultation, empathy, dialogue, closure, critical |
| Да / Нет | true / false |
| Разрешённое N/A | null |
| Неоценённый критерий | Весь диалог получает status=error, а не N/A |
| Числовая ступень | Число до применения веса: например dialogue=7, не 10.5 |
| Участок реплик a..b | Все исходные номера от a до b, включая бота, клиента и события |
| Исходная AI-оценка | status=ok, восемь критериев, rationale, evidence_turns и score |
| Ошибка/нет AI-оценки/устаревшая версия/частичные правила | status=error, criteria=[], score=null и причина |

В `model.name` перечисляются фактически использованные модели и модели состоявшихся попыток, включая неуспешные. Ollama — local; облачные сервисы — external_api; при их сочетании — hybrid. Если в группе вообще не было AI-оценок или попыток, приложение не придумывает название использованной модели.

Для успешных диалогов берутся **исходные ответы AI**, без ручных решений по апелляциям. История и результаты пересмотра по-прежнему доступны через обычный экспорт сверху сайта. Резюме и советы также остаются в обычной истории: официальная схема для них полей не задаёт.

Ошибки новой попытки не стирают прежнюю сохранённую оценку. Если последняя сохранённая оценка относится к текущей версии официального чек-листа, экспорт использует её; файлы не объявляют, что каждая последующая попытка была успешной.

Формат 1.0 фиксирует восемь кодов, веса и допустимые ступени. Пользовательский чек-лист с дополнительными критериями или другими весами нельзя молча преобразовать в этот формат: экспорт потребует вернуть официальную структуру и выполнить новую оценку. Изменения описаний при той же структуре допускаются; новая версия требует новых результатов.

В PDF `contact` допускает только true/false. Не следует автоматически превращать отсутствие приветствия в записи в false или разрешать null вопреки схеме: если полную допустимую оценку сформировать не удалось, применяется status=error. Разъяснение организаторов по этому случаю для звонков следует сохранить отдельно.

## До стоп-кода

На получение контрольного набора, анализ, проверку JSON, commit и push отведён один час. Оба файла должны быть доступны в открытом репозитории, ссылка на который заранее передана организаторам. Локальный commit без push не завершает сдачу.

Когда файлы проверены и репозиторий уже настроен, проверьте изменения перед отправкой:

```powershell
git diff -- results/dev/results.json results/prod/results.json
git add results/dev/results.json results/prod/results.json
git commit -m "Add CQA evaluation results"
git push
```

Эти команды не запускаются приложением автоматически. Ключи модели, локальная база и исходные выгрузки не должны попадать в публичный репозиторий. Сгенерированные файлы результатов предназначены для сдачи и не исключены через .gitignore.
