# Аналитика и проверка гипотез

Версия 0.5 дополняет обязательную оценку по чек-листу. Восемь критериев, расчёт весов и Results JSON 1.0 сохранены. Аналитические признаки не добавляются к официальным баллам и не выгружаются как новые критерии.

## Что открыть на сайте

1. **Обзор качества → фильтры.** Выберите группу данных, язык и канал. Покрытие показывает число полных исходных AI-оценок по актуальному чек-листу относительно всей выбранной группы. Ручные решения по апелляциям доступны в карточке; карта опирается на исходные ответы модели.
2. **Темы × нарушения критериев.** В ячейке, например, `2 / 5`: два нарушения среди пяти применимых оценок. N/A исключён; необработанные диалоги не считаются успешными. `—` означает отсутствие оценок. Нажмите ненулевую ячейку и увидите конкретные диалоги и основания нарушения. Нажатие на название темы показывает также ещё не оценённые обращения.
3. **Цитата → транскрипт.** Ссылка открывает диалог и выделяет исходные реплики. Так можно проверить смысл вывода, а не только цифру на дашборде.
4. **Сигналы затруднений.** Кнопка показывает явное непонимание и похожие повторные реплики после ответа оператора. Это кандидаты на ручной разбор. Длина диалога сама по себе не считается проблемой. Повторы до подключения оператора не штрафуют оператора.
5. **Итог разговора по тексту.** Фильтры различают решение, обещанное продолжение, открытые вопросы и недостаток данных. Старые результаты без резюме выделены отдельно.
6. **Карточка → Отдельные вопросы клиента.** Новый промпт `analysis-v3` разбирает существенные вопросы по отдельности. Для каждого есть исходный вопрос, ответ оператора при его наличии и статус. Если общий итог расходится с разбором вопросов, интерфейс просит пересмотр. Исходные выводы сохраняются; программа не исправляет смысл модели молча.
7. **Сравнение запусков.** Новые попытки фиксируют успехи, ошибки, время, известные токены и стоимость при заданных ценах. Если данные неизвестны, показывается пропуск с покрытием. Запрос после ошибки автоматически не повторяется. Старые успешные ответы видны отдельно: полного журнала старых неудачных запросов нет.
8. **Одни диалоги, разные конфигурации.** Сопоставляются последние сохранённые исходные ответы на общих ID при одинаковом чек-листе. Откройте расхождение, чтобы увидеть оба ответа, объяснения и цитаты. Расхождение само по себе не определяет правильный вариант.

Темы определяются по явным словам в репликах **клиента** на RU, KZ и EN. Это проверяемая категоризация по словарю, а не обученная кластеризация или embeddings. У диалога бывает несколько тем, поэтому суммы по темам могут превышать размер выборки. Неопознанные обращения попадают в «Другие».

## Какие гипотезы проверяем

Пороги ниже — наши предварительные критерии принятия решения, а не требования организаторов. Они фиксируются до эксперимента. Для выводов о точности нужен независимый человек; разметка ассистента не является Ground Truth.

| Гипотеза | Как проверять | Что измерять | Текущий статус |
|---|---|---|---|
| H1. Разбор каждого вопроса помогает замечать неполные ответы | На одних ID сравнить промпт с разбором и без него; модель и чек-лист одинаковые. Человек заранее выделяет вопросы и отвечает, какие закрыты | Пропущенные вопросы; ложные статусы «решено»; ошибки К4; конфликты резюме | Реализован вариант с разбором. Пилот проверяет работоспособность, полноценное сравнение ещё требуется |
| H2. Ошибка дополнительного резюме не должна терять корректную оценку | Повредить только insights в ответе с восемью валидными критериями; отдельно повредить основной критерий | Валидные баллы сохранены в первом случае; невалидная оценка отклонена во втором | Проверено автоматическими тестами |
| H3. Темы по словам достаточно полезны для первичного поиска | Независимо отметить темы для 18 чатов, по 6 на язык, затем сверить словарь. Разрешить несколько тем | Покрытие тем; точность назначений; пропуски по каждому языку. Предварительный порог: ≥80% корректных назначений | Механизм готов, независимая разметка отсутствует |
| H4. Карта с цитатами ускоряет поиск причины | Дать проверяющему 6 одинаковых задач поиска с картой и со списком, чередовать порядок. Засчитывать только верные находки | Медианное время до подтверждённой причины, число неверных находок. Цель: время меньше на ≥25% без роста ошибок | Интерфейс проверен, замер времени человеком не выполнен |
| H5. Более быстрая модель сохраняет приемлемое качество | Две модели, один промпт, одинаковые ID и правила, чередующийся порядок запуска; проверяющему скрыть названия моделей | Ошибки по каждому критерию, грубые ошибки отдельно; доля невалидных ответов, время, токены | Доступны журнал и парные расхождения; старые разные конфигурации не являются контролируемым A/B |
| H6. Эвристики затруднений полезны для отбора на пересмотр | Человек проверяет все срабатывания и равное число случайных несработавших чатов, не видя метки эвристики | Доля полезных срабатываний, пропущенные проблемы; отдельно бот и оператор | Механизм готов, независимая оценка отсутствует |
| H7. Режим medium уменьшит наблюдаемые смысловые ошибки относительно low | Одна модель, один промпт и те же три ID; сопоставить ответы и пропуски | К7 по составному правилу, полнота вопросов, время и токены | Разведочный пилот выполнен: наблюдаемые ошибки остались. Подробности в ANALYTICS_VALIDATION.md; общего вывода о режимах нет |

## Ближайший эксперимент

Пилот из трёх синтетических чатов: `p1-ru-027` (несколько вопросов), `p1-kz-009` (поиск бумаги и следующие шаги), `p1-en-014` (проверка личности и вопрос без ответа). Проверяем, что запрос завершается, все восемь критериев проходят валидацию, дополнительные блоки корректно ссылаются на роли и реплики, ошибки сохраняются в журнале. Эти три примера не дают оценки точности на всём наборе.

Для следующего сравнения зафиксировать две шестёрки, по два чата на язык. Первую использовать для настройки; вторую — один раз после заморозки промпта и правил. Независимый проверяющий размечает ответы до просмотра результатов моделей. Не менять настройки после просмотра контрольной шестёрки и не называть её результат оценкой на официальном контроле организаторов.

Рекомендованный порядок: сначала H2 и пилот, затем независимая проверка H1, после этого обработка оставшихся DEV и H4. Гипотезы о выручке, удержании и FCR требуют новых данных и не проверяются этим набором.

## Что объяснить жюри за минуту

«Мы оцениваем оператора по официальным правилам, а затем собираем оценки в карту проблем. Видно, какие темы связаны с нарушениями, сколько диалогов действительно оценено и на каких репликах основан вывод. Можно перейти из ячейки к исходному разговору и провести пересмотр. Новый анализ разбирает вопросы по отдельности, чтобы не терять второй вопрос за первым ответом. Журнал запусков помогает сравнивать качество и эксплуатационные затраты моделей. Мы не выдаём совпадение моделей за точность и не рассчитываем бизнес-эффект без CRM-данных».

## Ограничения

60 DEV-чатов синтетические; 5 звонков имеют ограничения транскрипции. Частоты характеризуют предоставленный набор, а не поток клиентов Freedom. В исходных полях нет подтверждённого результата из CRM, CSAT и общего идентификатора клиента. FCR, реальное удержание в боте, склейка сессий, влияние на отток/выручку и временной дрейф не измеряются. Уверенность модели не объявляется калиброванной вероятностью. Индексы и цитаты проверяются программно; смысловую достаточность доказательства проверяет человек.
