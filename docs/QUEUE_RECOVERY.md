# Восстановление фоновой очереди — 0.4.1

## Найденная причина

7 ноября 2026 наблюдалось: четыре задания в `queued`, ноль в `running`, ключ модели подключён. В журнале сервера найдена `sqlite3.OperationalError: disk I/O error` при чтении списка кандидатов. Исключение возникало за пределами обработки одного задания и завершало поток `cqa-queue`. HTTP-сервер продолжал отвечать, поэтому прежний health ошибочно показывал общую готовность.

Проверка SQLite `PRAGMA quick_check` вернула `ok`; перед исправлением сделана резервная копия базы. На диске оставалось приблизительно 255 МиБ. Недостаток свободного места зафиксирован как сопутствующее обстоятельство; точная причина ошибки ввода-вывода не установлена, повреждение базы проверкой не обнаружено.

## Исправление

- Ошибки доступа к базе больше не завершают цикл обработки. Обработчик повторяет доступ с интервалом около двух секунд и сообщает состояние `storage_error`.
- Если модель уже ответила, ответ остаётся в памяти обработчика до сохранения. Повторяется операция записи, а не запрос модели.
- Перед повтором записи проверяется транзакционная отметка завершённого задания: неопределённый результат COMMIT не создаёт вторую оценку.
- Если сбой произошёл при подтверждении старта, до отправки модели, задание получает явную ошибку для ручного повтора.
- Ошибка модели и приостановка остальных заданий при проблеме квоты/доступа сохраняются одной транзакцией.
- `/api/health` и `/api/jobs` показывают жив ли обработчик, его состояние, ID текущего задания и понятное описание сбоя. В браузере ошибка обработчика или обновления очереди видна отдельно от обычного ожидания.
- При ошибке SQLite HTTP API возвращает JSON с кодом `storage_unavailable` и статусом 503 вместо необработанного исключения.

Сохранение ответа в памяти защищает от временной недоступности базы только пока сервер работает. После остановки сервера неопределённый уже отправленный запрос по-прежнему не повторяется автоматически: задание становится прерванным и требует ручного решения.

## Проверки

Проходят **82 теста Python и 3 теста JavaScript**. Новые проверки воспроизводят временный отказ чтения SQLite, отказ сохранения после ответа модели, ошибку после успешного COMMIT, сбой подтверждения старта, повтор записи ошибки провайдера и HTTP 503. Во всех сценариях восстановления готового ответа модель вызывается не больше одного раза.

Четыре задания пользователя сохранены с исходными моделями и версиями чек-листа. Для работы новой версии сервер перезапущен, прежний ключ пользователь ввёл повторно. Эти действия не меняют исходные результаты анализа и не исправляют ответы модели вручную.

## Проверка восстановленной очереди на реальных заданиях

Все четыре ожидавших задания вышли из ожидания. `p1-en-002` успешно оценён (результат №11). Повторы по `p1-ru-003` и `p1-en-001` завершились соответственно ошибкой JSON и общей ошибкой обработки; запрос старого задания `p1-en-006` к Gemini 3.8 Flash завершился по сетевому ожиданию. Эти ошибки не выданы за успешные оценки, предыдущие результаты сохранены. Дополнительных заданий и автоматических повторных AI-запросов не создавалось.

После завершения очередь пуста, обработчик жив и находится в idle. DEV-выгрузка сформирована заново: 8 успешных оценок и 57 error, все 65 исходных ID учтены. Это подтверждение восстановления процесса; качество новых ответов модели отдельно не измерялось.
