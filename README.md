# CQA Studio

Прототип Conversation Quality Analytics для Freedom Broker / Data Challenge ’26.

Система показывает исходный разговор рядом с оценками, резюме и рекомендациями, связывает выводы с репликами и сохраняет историю апелляций. Чек-лист редактируется через интерфейс и применяется к новым диалогам без изменения кода. Проверки выполняются в сохраняемой фоновой очереди.

## Запуск

Требуется Python 3.11 или новее. Сторонних зависимостей для приложения нет.

```powershell
python server.py
```

Открыть **http://127.0.0.1:8765**. Либо запустить `start.cmd`.

Первый запуск импортирует локальный `research/dev.json`, если он доступен. В новом клоне используйте «Загрузить данные» для импорта JSON организаторов. Поддерживаются `data.records`, `records` и массив диалогов.

Для загрузки непосредственно через API задайте `CQA_DEV_URL` в окружении процесса или сохраните полученный от организаторов адрес в локальном `data/dev_source.txt`. Затем в «Загрузить данные» укажите `DEV` либо `group_id` контрольного набора и нажмите «Получить через API». Секретная ссылка не входит в репозиторий.

Сервер привязан к 127.0.0.1. Это локальный прототип без авторизации, не сервер для публичного доступа.

## Подключение AI

Настройки находятся в левом меню. Доступны:

- **Gemini / Google AI Studio:** ключ из https://aistudio.google.com/apikey, базовый адрес `https://generativelanguage.googleapis.com/v1beta/openai`, точное имя доступной модели. В локальной сессии проверена `gemini-3.8-flash`; обновление с резюме проверяется отдельно на `gemini-3.5-flash-lite`. Квота зависит от аккаунта. Для Gemini можно выбрать `low` или стандартный режим рассуждений.
- **OpenAI Responses API:** `https://api.openai.com/v1`; точное имя доступной модели указывается пользователем.
- **Совместимый Chat Completions API:** адрес с префиксом версии, например `https://<provider>/v1`, и имя модели.
- **Ollama:** `http://127.0.0.1:11434`, имя уже установленной локальной модели.

API-ключ хранится только в памяти серверного процесса и не возвращается браузеру. После перезапуска его нужно ввести заново. Альтернатива: переменная окружения `CQA_API_KEY` или `OPENAI_API_KEY`. Провайдер, URL и название модели сохраняются в SQLite; ключ — нет.

Цена за миллион входных и выходных токенов задаётся в настройках вручную по тарифу провайдера. Если цены или usage отсутствуют, стоимость не выдумывается. Одна попытка оценки делает один запрос модели для критериев, резюме и рекомендаций; ручной повтор — новый запрос. Даже отклонённый по схеме ответ может расходовать квоту. Очередь выполняет запросы последовательно; при HTTP 429/401/403 остальные ожидающие задания приостанавливаются до ручного возобновления. При других ошибках обработчик переходит к следующему заданию.

При запуске проверки облачная модель получает текст выбранного диалога и чек-лист. Для первых экспериментов используйте синтетические чаты DEV. Доступность квоты и правила обработки реальных разговоров нужно учитывать при выборе провайдера.

## Что работает

- Список диалогов, поиск, фильтры по языку, каналу и состоянию.
- Исходные роли и временные метки RU/KZ/EN, скрытие бота и системных событий.
- Плеер записей и ссылка на оригинальное аудио.
- Редактор критериев: текст, вес, допустимые ответы, числовая шкала, N/A, секция, отдельный флаг грубой ошибки; добавление и удаление критериев.
- Сохранение новой версии чек-листа, пометка прежних оценок как устаревших.
- AI-оценка через подключённого провайдера. Ответы проверяются на полноту, допустимость значений и точность цитат до сохранения.
- Резюме: запрос клиента, действия оператора, итог и статус — решено / ожидается продолжение / не решено / недостаточно данных.
- Адресные рекомендации: отдельный совет на каждый нарушенный критерий, с переходом к исходным сообщениям.
- Фоновая очередь SQLite: прогресс, защита от дублей, снимок правил и модели, ожидание ключа, явный повтор ошибок. Обновление страницы не прерывает запрос; прерванный при перезапуске сервера запрос не повторяется автоматически.
- Переход от доказательства к реплике или участку транскрипта.
- Апелляция с комментарием; отдельное решение проверяющего с причиной; пересчёт итога и сохранение исходного результата.
- Обзор фактических результатов и экспорт оценок/истории в JSON.
- Отдельный экспорт Results JSON 1.0 для жюри: все 65 DEV-диалогов либо 10 контрольных чатов, точные коды и типы, явные ошибки; независимый валидатор файла.
- SQLite-хранилище, транзакционные обновления, неизменяемый исходный транскрипт по ID.

## Границы готовности

**Первый реальный запуск Gemini 3.8 Flash описан отдельно в [docs/VALIDATION.md](docs/VALIDATION.md): 6 разговоров, 48 ответов по критериям. Обобщённая точность ещё не измерена.** В новом клоне до ввода ключа приложение работает в явно обозначенном режиме «Проверка правил»: заполняет только отдельные формальные признаки и оставляет смысловые критерии неоценёнными. Итог отсутствует до заполнения всех критериев. Резюме в этом режиме не генерируется. Результаты правил не называются оценками LLM. Воспроизведение запросов требует собственного ключа и квоты.

Наличие цитаты и совпадение текста проверяются автоматически; доказательность вывода по смыслу всё равно требует проверки. Фактическая правильность консультаций ограничена отсутствием официальной базы знаний по продуктам. Для голосовых разговоров текст не доказывает дикцию или интонацию; точка начала аудио относительно ISO-меток также не подтверждена. Переход к реплике есть, точный переход к секунде записи не заявляется.

Исследовательская разметка 12 диалогов в `research/` выполнена ассистентом, не является Ground Truth жюри и не прошла независимую человеческую проверку. 17 спорных оценок отмечены отдельно. Нельзя выдавать совпадение с ней за точность относительно жюри.

## Расчёт

Для каждого применимого критерия:

```text
нормализованная оценка = 1 или 0 для Да/Нет; значение / максимум для числовой шкалы
итог = ROUND(100 × Σ(вес × нормализованная оценка) / Σ(применимые веса), 2)
```

N/A исключается из обеих сумм. Грубая ошибка — независимый флаг, не обнуление итога. Промежуточные значения не округляются. Режим для точных половин выбран HALF_UP: PDF задаёт два знака, но не уточняет режим округления. Если нет применимых весов или есть незаполненные критерии, числового итога нет.

## Архитектура

```text
HTML / CSS / JavaScript
        ↓ JSON / HTTP
Python HTTP API ── SQLite
        ├── импорт DEV / контрольного набора
        ├── версии чек-листов и апелляции
        ├── проверка JSON, цитат и расчёт баллов
        ├── сохраняемая очередь → один фоновый обработчик
        ├── резюме и советы → проверка ссылок на исходные реплики
        └── адаптер модели: Gemini / OpenAI / совместимый API / Ollama
```

`cqa/domain.py` — правила данных и расчёт; `cqa/providers.py` — модель; `cqa/insights.py` — проверка резюме, рекомендаций и отдельных вопросов; `cqa/analytics.py` — карта тем, признаки затруднений и сравнение запусков; `cqa/queue.py` — обработчик заданий; `cqa/store.py` — хранение; `cqa/engine.py` — ограниченная проверка правил; `server.py` — HTTP API; `static/` — интерфейс. Интерфейс не зависит от внешних CDN, шрифтов и библиотек; его можно далее адаптировать к HTML-компоненту Dynamics 365. Интеграция с Dynamics 365 сейчас не реализована.

Новые инструменты и проверяемые гипотезы: [docs/ANALYTICS.md](docs/ANALYTICS.md). Аналитика использует исходные AI-оценки текущего чек-листа и показывает покрытие. Дополнительные блоки проверяются независимо от официальных восьми критериев. Results JSON 1.0 не меняется.

В критериях модель возвращает точные цитаты, которые сервер сверяет с транскриптом. В резюме и советах модель указывает номера реплик, а сервер копирует их исходный текст. Это исключает искажение текста при повторной генерации цитат, но не доказывает смысловую верность самого вывода.

## Проверка

```powershell
python -m unittest discover -s tests -v
node --check static/app.js
node --test tests/*.test.cjs
```

Тесты покрывают N/A и шкалы, апелляции, версии, защиту исходных данных, границы цитат, рекомендации только по нарушениям, очередь и восстановление, обработку квот и локальный HTTP-сценарий. Внешний модельный адаптер в unit-тестах проверяется на заглушке; реальные эксперименты описываются отдельно.

Для изолированной проверки интерфейса:

```powershell
python server.py --port 8766 --db data/qa.sqlite
```

## План оценки качества

1. Подключить модель и оценить один чат на каждом языке.
2. Проверить фактические цитаты, N/A, грубые ошибки и ответы по шкалам; согласовать спорную разметку с человеком.
3. Запустить парный эксперимент: обычная оценка против обязательных доказательств. Подготовленные задания находятся в `research/experiment/requests.jsonl` (генерируются локально и не публикуются).
4. Использовать 6 диалогов для настройки и 6 для локальной проверки, без подгонки разметки под модель. Записывать модель/версию, токены, задержку, пропуски грубых ошибок и расхождения по критериям.
5. Проверить новый критерий, не использованный при настройке, и затем контрольные диалоги организаторов.

## Для сдачи

Название команды: **Fantastic Four**. Раздел **«Сдача жюри»** сохраняет официальные файлы в `results/dev/results.json` и `results/prod/results.json`. Полная инструкция и команды проверки — [docs/SUBMISSION.md](docs/SUBMISSION.md). Обычная кнопка экспорта сверху по-прежнему выгружает внутреннюю историю, а не файл для жюри.

```powershell
python -X utf8 submission.py export --set dev --team "Fantastic Four"
python -X utf8 submission.py check results/dev/results.json --set dev
```

Неоценённые диалоги включаются со статусом `error`; пустой контрольный файл до получения данных не создаётся. Сохранение локально не выполняет push и не завершает сдачу.

Открытый Git-репозиторий с кодом и инструкцией запуска. Секреты API, локальная SQLite-база, аудиоссылки и выгрузки разговоров исключены через `.gitignore`. README описывает ограничения прямо; результатов качества модели, которые ещё не измерены, в нём нет.

Пошаговое использование: [docs/USER_GUIDE.md](docs/USER_GUIDE.md). Объяснение архитектуры, сценарий выступления и ответы жюри: [docs/JURY_GUIDE.md](docs/JURY_GUIDE.md).
